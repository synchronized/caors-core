# v0.5.0：资源显式刷新与分块读取

## 状态

规划中，alpha，2026-10-20 建立；版本范围为建议稿，关键语义尚待用户确认，未开始运行时开发。
维护入口为本页及关联 Plan。当前公开版本仍为 [v0.4.0](v0.4.0.md)，工程版本保持
[caors_version.cmake](../../cmake/caors_version.cmake) 的现值，发布准备阶段才调整。
需求来自 Gneiss 的 UPSTREAM-051-caors-vfs-followups.md，基线 cbe41b75223f52bec746cc23346b28eba90fa693。
本仓库维护本地方案，不修改上游提案，也不声明联合接入已完成。

## 建议范围与非目标

建议交付显式选择新来源的单资源刷新、迟到结果发布保护、串行分块聚合与受控逐块消费，
并完成来源快照成本基准及方案结论。快照优化为条件范围：有收益且失效规则可证明时实施；
否则交付基线与保持现状的理由，不将“未优化”记为优化验收通过。

不包含自动全库刷新、缓存驱逐或对象销毁的统一操作、依赖闭包原子发布、场景事务、
多块并行预读、通用异步流框架、内置 libuv、GPU/资产格式逻辑、稳定 C++ ABI 或预编译 SDK。
首版刷新只处理单资源；显式依赖刷新策略作为后续扩展，原因是跨资源选择与发布需要独立事务设计。
恢复条件为确定依赖闭包与共享规则并单列验收；不阻塞明确限定的单资源刷新交付。

## 交付契约

交付源码与可安装 CMake 包，验证 Windows/Linux x64、项目规定编译器及共享/静态组合。
不新增第三方运行时依赖，宿主提供 executor/loop；公共布局或 API 变化需统一重编译宿主与插件。
旧同步/异步 IO 契约继续由参考维护；本文候选接口不代表已有能力。

## 发布门槛与证据

三个 Plan 的确定范围完成；刷新竞争、分块取消/背压、模块与 allocator 寿命、安装迁移回归通过。
按 [CI 策略](../guides/ci.md)在关键集成批次运行 Linux 5 / Windows 3 与相关压力，
不逐中间提交重复矩阵；最终发布 SHA 遵循[发布清单](../checklists/release-readiness.md)。
性能结果须记录环境与提交，不能用共享 CI 耗时作正式性能承诺。
Windows/Linux 固定环境测量无法完成时应先明确收窄版本范围或等待，不静默勾选通过。

尚无本版运行时测试、性能数据、tag 或 Release；实施后建立独立 Record，测量摘要进入 benchmarks/results。
真实 Gneiss/libuv 联调仍由宿主环境执行，不是本版通用协议交付的前置条件；已发现的正确性缺陷必须先解决。
