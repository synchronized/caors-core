# 来源快照复制成本评估与复用边界

## 状态与已知事实

讨论中，C51-10，目标范围见 [v0.5.0](../versions/v0.5.0.md)。当前没有本议题性能测量。
provider::snapshot 遍历全部 GUID 绑定，复制位置并捕获路由，成本随绑定数增长；不能直接称为卡顿根因。
普通单资源 request_load 的 cache 命中及在途共享先于快照捕获；database 的两类 preload
会在批次入口捕获快照，因此须分开测量，不能笼统声明命中路径都零捕获。
现有实现与契约见[资源参考](../reference/resources.md#加载来源快照)。

## 基准计划

- 绑定规模 1 千、1 万、10 万；单/多后端、嵌套路由、短/长路径、同批依赖共享。
- 首次捕获、无修改重复捕获、rebind/unbind/remount 后、连续修改后；测量更新本身。
- 分开覆盖单资源 cache 命中、在途共享、首次实际操作、typed/dispatched preload 批次及其命中情况。
- 记录捕获线程、提交、preset、OS/CPU/编译器、预热与样本次数、分位数和最大值。
  分位数基于逐次样本，不用三次汇总均值冒充分位数；按结果规范至少独立运行三次并保留可复核数据。
- 记录显式 allocator 和可观察的全局分配次数/字节、峰值内存、旧快照保留量及写入耗时。
  无法完整跟踪的分配域必须注明，不把 allocator 局部统计当进程总内存。
- Windows/Linux 固定环境 Release，优化前后同机同负载；Debug 和共享 CI 只辅助正确性。

## 比较方案与建议

| 方案 | 可能收益 | 主要约束 |
| --- | --- | --- |
| 保持全量复制 | 最简单，行为已验证 | 测量判断真实开销是否可接受 |
| 同修订复用不可变快照 | 避免无变化时重复复制；优先研究 | 必须观察 provider、source 和所有嵌套路由变化 |
| 绑定表写时复制/结构共享 | 捕获轻量、小更新可共享 | 写停顿、旧版本内存滞留、同步和模块寿命复杂 |
| 仅捕获依赖闭包 | 小请求减少复制 | 动态依赖尚未知，容易破坏同次加载来源契约 |

先建立基线，推荐先试可验证的修订复用；不预设必须优化或固定加速倍数。
仅 provider generation 不是有效缓存键；根未变也可能发生嵌套 remount。
外部自定义 source 无可观察修订时，候选选择为不复用（推荐默认）、显式冻结配置或宿主显式通知。
不能默默依赖调用方通知而继续宣称自动捕获最新路由；修订检查与捕获的并发窗口必须明确。
路由修订不检测磁盘内容，不能当内容 hash；刷新发布序号也不是快照复用键。

建议先复用每个 source 的冻结节点以减少重复捕获工作，再评估全快照共享；是否足够必须由数据判断。
仅复用冻结路由节点不会消除 GUID/路径的全表复制，必须分别报告两部分成本，不能据此宣称捕获 O(1)。
复用缓存不得强持有所有历史版本：明确保留最新条目、弱引用或显式上限，并测量宿主持有旧快照时的真实内存。
配置更新继续遵守既有外部同步约束，不无意扩大 provider 的线程安全承诺。
