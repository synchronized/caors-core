# 资源显式刷新与默认绑定发布顺序

## 状态与问题

已完成，C51-08，目标范围见 [v0.5.0](../versions/v0.5.0.md)。2026-10-20 用户确认采用下列推荐方案；替代方案保留为取舍依据。
当前行为见[资源参考](../reference/resources.md#加载来源快照)。源码基线为 cbe41b75：
request_reload_into_impl 要求已有缓存，同 GUID 有在途操作时优先加入它，然后才可能捕获新快照。
因此 remount 后 reload 不保证立即选择新来源；这是既有共享契约，不追认成已证实缺陷。

## 候选方案

| 方案 | 收益 | 代价与限制 |
| --- | --- | --- |
| 保持 API，等待旧操作结束再 reload | 最小改动 | 宿主自行等待，无法直接表达并行准备新来源 |
| 改写 reload 为每次强制新操作 | 名称少 | 改变旧共享语义，可能产生意外重复工作 |
| 新增显式刷新操作，保留 load/reload | 意图明确、迁移可控 | 增加接口及发布序号状态；推荐 |
| 来源版本使用独立资源上下文 | 多项目隔离清晰 | 管理和内存成本高，不能替代共享 cache 内的刷新 |

## 建议修改

采用 request_refresh<T>(guid)，同时经 database、asset_manager、asset_group 转发，
worker/completion 继续使用 manager/group 默认配置；准确签名与当前行为由参考及公共头维护。
新操作捕获新的 provider 快照，不加入旧 load/reload；无旧缓存时也可准备并发布首次对象。
不引入隐式失效、驱逐或对象销毁，保留外部旧 handle 的所有权。

建议按“资源类型 + GUID + cache 身份”维护单调推进的发布凭据（内部使用不可复用的拥有式身份，不暴露递增整数），并同步保护所有能写默认绑定的路径：
普通首次 load、旧 reload、新 refresh。仅保护 refresh 之间不足以阻止旧 load 迟到覆盖。
刷新序号与进程内 source_id、provider 配置修订、内容修订分别管理。

### 已确认的发布与失败语义

- 普通 load 仍优先返回已发布缓存；无缓存时建议加入当前选定操作，不能重新加入已失去发布资格的旧操作。
- 每次显式刷新都创建新操作；首版不按来源自动合并两次刷新，避免把磁盘原地变更误当同内容。
- 登记有效刷新意图时占用新发布序号；参数无效或意图登记前分配失败不改变序号。
  意图登记后，即使 worker 拒绝、取消或读取失败，也不恢复更早操作的发布资格。
- 只有当前序号可在指定 completion executor 上原子更新单资源默认绑定；失败保留此前已发布对象。
- 旧操作不强制取消，已有订阅仍需收尾；建议允许其返回自己加载的旧版本 handle，但禁止发布到默认 cache。
  该做法需要拆分“构造拥有式结果”和“写 cache”；替代方案为明确 superseded 终态，不能伪报成功或取消其他订阅。
- 最新刷新 B 失败时保留原已发布 A，不允许更早尚在途的 C 因 B 失败而重新取得发布资格。
- 首版仅刷新根资源；依赖可能命中旧缓存，必须明确不承诺依赖闭包内容一致。
  需要一致依赖集合时由宿主使用独立上下文/显式协调，不将共享快照等同于内容事务。
- 现有线程约束不扩大；序号检查与 cache 更新须处于同一合法发布临界区，不能先检查后另行排队写入。
