# Windows Clang 资源协程基准

## 环境与方法

- 日期：2026-08-07；
- 分支：`feature/asio-task-redesign`；
- 基线提交：`1a320c0`，测量代码随本结果一同提交；
- preset：`windows-clang-benchmark`，Release；
- 每个场景执行 100,000 轮，完整程序独立运行三次；
- 延迟以 16 次操作为一批，共采集 6,250 个样本并输出 p50、p95 和最大值；
- 分配统计只覆盖传入请求的 `memory_resource`，不包含由全局分配器创建的协程帧。

这些数据用于建立当前实现的基线，不能替代真实资源加载 workload 或固定 Linux 环境下的正式复验。

## 分配结果

| 场景 | 每轮分配次数 | 每轮累计分配字节 | 峰值存活字节 | 结束时存活字节 |
| --- | ---: | ---: | ---: | ---: |
| 请求已完成 | 1.00001 | 48.0026 B | 312 B | 0 B |
| 单等待者 | 3 | 336 B | 336 B | 0 B |
| 四等待者 | 9 | 696 B | 624 B | 0 B |

“请求已完成”场景会在 100,000 次等待前创建一次可复用请求，因此总数比每轮一次多一次分配。
所有场景结束后均无请求资源泄漏。

## 延迟结果

单位为 ns/操作；表中保留三次独立运行结果。

| 场景 | 第一次 p50 / p95 / max | 第二次 p50 / p95 / max | 第三次 p50 / p95 / max |
| --- | ---: | ---: | ---: |
| 请求已完成 | 193 / 206 / 993 | 193 / 206 / 1,793 | 193 / 206 / 1,350 |
| 单等待者 | 431 / 443 / 1,281 | 431 / 443 / 3,043 | 437 / 456 / 6,712 |
| 四等待者 | 1,400 / 1,500 / 9,012 | 1,456 / 1,537 / 5,987 | 1,450 / 1,525 / 1,704,468 |

第三次四等待者的最大值出现约 1.7 ms 的系统抖动，但 p50/p95 与前两次接近。因此后续回归判断应以
p50/p95 为主，最大值只用于发现异常长尾。

## 结论

- 初始基线中，请求已完成路径的 p50/p95 稳定在 193/206 ns，但仍发生约一次请求资源分配；
- 单等待者稳定为每轮 3 次请求资源分配，p50 为 431–437 ns，p95 为 443–456 ns；
- 四等待者稳定为每轮 9 次请求资源分配，p50 为 1,400–1,456 ns，p95 为 1,500–1,537 ns；
- 当前结果只建立性能和分配基线，不授权把协程路径接入更多组件；仍需 Linux 正式复验和真实 workload
  决定后续优化优先级。

## Ready fast path 复测

awaiter 改为仅在确实进入 `await_suspend()` 时创建等待状态后，使用相同 preset 和 100,000 轮参数复测：

| 场景 | 总分配次数 | 每轮分配次数 | p50 | p95 | max |
| --- | ---: | ---: | ---: | ---: | ---: |
| 请求已完成 | 1 | 0.00001 | 125 ns | 137 ns | 943 ns |
| 单等待者 | 300,000 | 3 | 431 ns | 443 ns | 1,812 ns |
| 四等待者 | 900,000 | 9 | 1,406 ns | 1,512 ns | 7,550 ns |

ready 场景唯一一次请求资源分配来自预先创建并重复使用的请求状态；100,000 次等待不再创建辅助状态。
相对初始基线，ready p50 约下降 35%，p95 约下降 33%，挂起路径的分配次数和延迟保持在原波动范围内。
