# Windows Clang 来源快照成本对比

## 环境与方法

2026-10-20，Windows 10 专业版 10.0.19045，Intel Core i5-8600K @ 3.60GHz，6 核/6 逻辑 CPU，
Clang 23.1.1 / MSVC ABI，Shared Release，C++20。构建目录 build/v050-bench，
使用 windows-clang-release 并开启 CAORS_BUILD_BENCHMARKS；测量期间未运行本机构建。

基线提交 d59cbb6e83698103594082d6dc30523ab1a25301；优化提交 602183206f2c28bd7b3fb294456a81f7ca5c8d78。
两者使用同一基准程序与参数：`caors_provider_snapshot_benchmarks 31 0 <逐次样本.csv>`。
每个暖态用例预热 3 次、测量 31 次，前后各独立执行 3 轮，没有剔除异常样本。
执行顺序为先三轮基线再三轮优化，未随机交错；环境趋势和背景干扰未被完全消除。
first_capture 是每个新 provider 的单次首次捕获，逐次数据保留，但不混入下表暖态分位数。
GUID 为确定性序列，绑定数 1000/10000/100000，来源数 1/8，短/长路径，平坦/嵌套路由。

下表列三轮各自 p50（ms）；变化量使用三轮 p50 的中位数计算，缩短为正。
p99 列为三轮 p99 的最大值（ms），不是把三轮数据混合计算的新分位数。
cache_hit/inflight_join/全命中 preload 不执行捕获，其微小差异视为对照噪声，不归因为本优化。
计时仅覆盖捕获，不含快照析构；请求路径另计相应请求及局部结果清理。

## 结论与边界

同次捕获按 source 身份临时复用冻结根后，source::freeze_routes 调用从绑定数降为不同来源数。
下一次捕获仍重新冻结，不依赖无法完整观察的外部 generation；嵌套 remount 不被缓存遮蔽。
测试范围内大索引捕获的三轮中位数有改善，但 GUID/路径仍全量复制，捕获仍为 O(N)。

部分用例存在明显长尾，优化后个别轮次/尾部分位数更差，原因尚未定位；不能宣称所有轮次或尾延迟改善。
本数据不证明 Gneiss 卡顿根因，不提供正式环境低延迟保证。更严格的尾延迟复验仍需控制环境干扰。

分配统计仅覆盖传入 provider 的显式 allocator；不覆盖所有 STL、控制块、后端 allocator 或进程内存。
例如 10 万短路径单来源 capture，显式分配次数由 100013 增至 100016，分配字节增加 224；
不能把冻结调用减少混称为已测得的全局分配次数下降。
临时复用表增加 O(不同 source 数) 元数据；来源数接近绑定数的场景未测，不能泛化当前收益。
retain4 由 fixture 保留四份旧快照，捕获时另有当前候选；峰值列包含 fixture，并非库强制的内存上限。
库不跨次保存历史快照，宿主持有多份快照仍自行承担 O(快照份数 × 绑定数) 存储。

固定 Linux Release 性能复验未完成：本机没有可用固定 Linux 环境，恢复条件为提供固定主机并在同机比较上述提交。
共享 CI smoke 仅证明基准可编译运行，不替代此项，不能标为跨平台性能验证通过。
